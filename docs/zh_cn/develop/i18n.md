# 界面本地化

客户端展示的 M9A 项目文本——任务名称、选项标签、说明、预设、资源与控制器名称——来自 `interface.json` 和 `tasks/` 下的文件。这些字符串通过 MaaFramework Project Interface V2 的国际化机制进行本地化。

## 工作方式

`interface.json` 中声明可用的翻译文件：

```json
"languages": {
    "zh_cn": "locales/zh_cn.json",
    "en_us": "locales/en_us.json"
}
```

路径相对于 `interface.json` 所在目录。M9A 将这些 Project Interface 资产放在项目根目录的 `locales/` 中，而不是 `resource/`；后者只存放 MaaFW 运行资源。（`i18n` 指国际化机制，`locales` 指语言数据目录。）每个翻译文件都是「键 → 译文」的扁平映射：

```json
{
    "Task.Wilderness": "收取荒原",
    "Option.Wilderness.Wellspring": "好梦井"
}
```

任何支持国际化的字段，只要其值以 `$` 开头，就会被当作翻译文件中的键。客户端按当前语言解析该键。缺少译文时的回退行为取决于客户端，可能显示键本身或回退到稳定名称，因此所有引用都必须通过 `pnpm check:i18n` 保证完整。

```json
{
    "name": "收取荒原",
    "label": "$Task.Wilderness",
    "entry": "Wilderness"
}
```

## `name` 是 ID，不是显示名

`name` 是稳定标识符。它会被写入用户配置文件，并被预设的任务列表以及各任务的 `option` 数组引用，因此**重命名会破坏用户已有的配置**。它保持中文原样不变，显示文本改由 `label` 提供。

`option` 映射的键和 `cases[].name` 同理：在旁边新增 `label`，绝不要改写键本身。

如果某个 `case` 的 `name` 在各语言下写法一致（`Yes`、`No`、`24h`、`MAX`、纯数字等），则无需 `label`，客户端会回退显示 `name`；但其 `description` 仍可能需要一个键。

## 支持填键的字段

`label`（任务、选项与项目层级）、`description`、`desc`、`pattern_msg`、`icon`、`doc`、`title`、`contact`、`license`、`welcome`。注意 `pipeline_override` 属于面向游戏的 pipeline 数据，不参与翻译。

`icon`、`license`、`contact` 的字面量是路径或标识，允许保持字面量；其余文本字段在声明了 `languages` 之后，字面量一律算未翻译——不限语言，因为字面量不可能跟随界面语言切换。

pipeline 的 `focus` 消息模板同样支持键。`focus` 是「消息类型 → 模板」，模板字符串或其 `content` 以 `$` 开头即视为键。其余 pipeline 字段（`desc`、`expected` 等）不参与翻译；`focus` 之外以 `$` 开头的值可能是表达式引用（如 `$0`），因此脚本只扫 `focus.*.content`。

## 键命名规范

键使用 ASCII、以点分隔，结构与字符串出现的位置一致：

| 类型       | 格式                                                       | 示例                                |
| ---------- | ---------------------------------------------------------- | ----------------------------------- |
| 任务       | `Task.<Name>`                                              | `Task.BalancedFarming`              |
| 任务说明   | `Task.<Name>.desc`                                         | `Task.BalancedFarming.desc`         |
| 选项       | `Option.<Task>.<Option>`                                   | `Option.Combat.StageType`           |
| 选项 case  | `Option.<Task>.<Option>.<Case>`                            | `Option.Combat.StageType.MainStory` |
| 选项输入框 | `Option.<Task>.<Option>.<Input>`                           | `Option.Combat.StageCustom.Chapter` |
| 预设       | `Preset.<Name>`                                            | `Preset.DailyIdle`                  |
| 欢迎公告   | `Welcome.<Index>`                                          | `Welcome.1`                         |
| 焦点消息   | `Focus.<Task>.<Reason>`                                    | `Focus.Combat.StageNotFound`        |
| 接口层级   | `Interface.Label`、`Controller.*`、`Resource.*`、`Group.*` | `Resource.GlobalEn`                 |

说明追加 `.desc`，`pattern_msg` 追加 `.msg`。被多个选项共用的字符串（例如编队序号）使用 `Common.*` 键，只需翻译一次。

## 新增任务的流程

1. 照常在 `tasks/` 下编写任务，`name` 保持中文。
2. 添加 `"label": "$Task.<Name>"`；若有说明，再添加 `"description": "$Task.<Name>.desc"`。
3. 在 `locales/zh_cn.json` 和 `locales/en_us.json` **两个文件**中补上对应条目。
4. pipeline 里新增 `focus` 消息时，`content` 写成 `$Focus.<Task>.<Reason>` 并同样补两个语言文件。
5. 运行 `pnpm check:i18n`。

## 校验

`pnpm check:i18n` 已并入 `pnpm check`，出现以下情况会导致校验失败：

- 某个 `$key` 引用在语言文件中缺少对应条目（含 pipeline `focus` 消息）
- 语言文件中存在已无人引用的条目
- 两个语言文件的键集合不一致
- 声明了 `languages` 之后，文本字段仍写着字面量——不限语言，`icon`、`license`、`contact` 除外
- 同一个键在语言文件里定义了多次
- `interface.json`、task 文件或 pipeline 文件无法解析

未声明 `languages` 的项目只检查无处解析的 `$key`，单语言项目不会被判失败。

## 新增语言

在 `interface.json` 的 `languages` 中添加文件，复制 `locales/zh_cn.json` 作为起点并翻译其值即可。校验要求新文件的键集合与现有文件完全一致。

## 后续扩展：多命名空间

`locales/` 只承载 Project Interface 界面文案，因此现在是 `<lang>.json` 的扁平结构——语言在最外层，与 Rails、gettext、Chrome、Android 等主流约定一致。

将来 agent 若也需要自己的文案，沿用同一分层方式扩展为 `<lang>/<namespace>.json`（`locales/zh_cn/interface.json`、`locales/zh_cn/agent.json`），并同步 `interface.json` 的 `languages`。届时 `tools/build-release.mjs` 需要改为打包整个 `locales/` 目录——它现在只打包 `languages` 中显式声明的文件，新增的命名空间不会自动进发布包。
