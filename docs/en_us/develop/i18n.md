# Interface Localisation

The M9A project text rendered by clients — task names, option labels, descriptions, presets, resource and controller names — comes from `interface.json` and the files under `tasks/`. Those strings are localised through the MaaFramework Project Interface V2 i18n mechanism.

## How it works

`interface.json` declares the available translation files:

```json
"languages": {
    "zh_cn": "locales/zh_cn.json",
    "en_us": "locales/en_us.json"
}
```

Paths are relative to the directory holding `interface.json`. M9A keeps these Project Interface assets in the root-level `locales/` directory rather than `resource/`, which is reserved for MaaFW runtime resources. (`i18n` names the mechanism; `locales` names the data.) Each translation file is a flat map of key to translated text:

```json
{
    "Task.Wilderness": "Collect Wasteland",
    "Option.Wilderness.Wellspring": "Wellspring"
}
```

Any i18n-capable field whose value begins with `$` is treated as a key into those files. The client resolves it against the active language. Missing-key fallback is client-dependent and may expose the key or fall back to the stable name, so every reference must be covered by `pnpm check:i18n`.

```json
{
    "name": "收取荒原",
    "label": "$Task.Wilderness",
    "entry": "Wilderness"
}
```

## `name` is an ID, not a label

`name` is the stable identifier. It is written into user configuration files, referenced by preset task lists and by the `option` arrays on each task, so **renaming it breaks existing user configurations**. It stays as-is — in Chinese — and the display string is supplied by `label` instead.

The same applies to `option` map keys and to `cases[].name`. Add a `label` beside them; never rewrite the key itself.

A `case` whose `name` already reads the same in every language (`Yes`, `No`, `24h`, `MAX`, a bare number) does not need a `label` — the client falls back to `name`. It may still need a key for its `description`.

## Fields that take a key

`label` (at the task, option and project level), `description`, `desc`, `pattern_msg`, `icon`, `doc`, `title`, `contact`, `license` and `welcome`. Note that `pipeline_override` is game-facing pipeline data and is never translated.

`icon`, `license` and `contact` hold a path or an identifier, so a literal there is allowed. Every other text field must be a `$key` once `languages` is declared — in any language, not just Chinese, because a literal cannot follow the interface language.

A pipeline `focus` message template takes keys too. `focus` maps a message type to a template, and a template string — or its `content` — starting with `$` is a key. Other pipeline fields (`desc`, `expected`, …) are not translated, and a `$`-shaped value outside `focus` may be an expression reference such as `$0`, so the script only scans `focus.*.content`.

## Key naming

Keys are ASCII and dot-separated, mirroring where the string appears:

| Kind             | Pattern                                                    | Example                             |
| ---------------- | ---------------------------------------------------------- | ----------------------------------- |
| Task             | `Task.<Name>`                                              | `Task.BalancedFarming`              |
| Task description | `Task.<Name>.desc`                                         | `Task.BalancedFarming.desc`         |
| Option           | `Option.<Task>.<Option>`                                   | `Option.Combat.StageType`           |
| Option case      | `Option.<Task>.<Option>.<Case>`                            | `Option.Combat.StageType.MainStory` |
| Option input     | `Option.<Task>.<Option>.<Input>`                           | `Option.Combat.StageCustom.Chapter` |
| Preset           | `Preset.<Name>`                                            | `Preset.DailyIdle`                  |
| Welcome notice   | `Welcome.<Index>`                                          | `Welcome.1`                         |
| Focus message    | `Focus.<Task>.<Reason>`                                    | `Focus.Combat.StageNotFound`        |
| Interface level  | `Interface.Label`, `Controller.*`, `Resource.*`, `Group.*` | `Resource.GlobalEn`                 |

Append `.desc` for a description and `.msg` for a `pattern_msg`. Strings shared by several options (for example the formation slot numbers) use a `Common.*` key so they are translated once.

## Adding a new task

1. Write the task in `tasks/` as usual, keeping `name` in Chinese.
2. Add `"label": "$Task.<Name>"`, and `"description": "$Task.<Name>.desc"` if it has one.
3. Add the matching entries to **both** `locales/zh_cn.json` and `locales/en_us.json`.
4. When adding a `focus` message in the pipeline, write its `content` as `$Focus.<Task>.<Reason>` and add that entry to both files as well.
5. Run `pnpm check:i18n`.

## Validation

`pnpm check:i18n` runs as part of `pnpm check` and fails the build on:

- a `$key` reference with no entry in one of the language files (pipeline `focus` messages included)
- an entry in a language file that nothing references any more
- the two language files covering different key sets
- a text field still holding a literal once `languages` is declared — in any language, except `icon`, `license` and `contact`
- a key defined more than once in a language file
- an `interface.json`, task file or pipeline file that cannot be parsed

A project that declares no `languages` is only checked for `$key` references it cannot resolve, so a single-language project is never failed for literal text.

## Adding a language

Add the file to the `languages` block in `interface.json`, copy `locales/zh_cn.json` as a starting point and translate the values. The validator requires the new file to cover exactly the same key set as the existing ones.

## Extending later: multiple namespaces

`locales/` carries Project Interface display text only, so it is flat today — `<lang>.json`, with the language outermost, matching the prevailing convention (Rails, gettext, Chrome, Android).

If the agent later needs its own text, extend along the same axis to `<lang>/<namespace>.json` (`locales/zh_cn/interface.json`, `locales/zh_cn/agent.json`) and update the `languages` block to match. At that point `tools/build-release.mjs` must package the whole `locales/` directory; today it packages only the files explicitly declared in `languages`, so a new namespace would not ship automatically.
